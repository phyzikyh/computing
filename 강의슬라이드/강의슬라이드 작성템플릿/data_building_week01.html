3. 모델보다 먼저 만나는 문제

  • 필요한 데이터가 부족합니다.
  • 값이 비거나 형식이 제각각인 지저분한 데이터입니다.
  • 정답이 틀리거나 기준이 흔들리는 라벨 오류가 있습니다.
  • 특정 집단이나 상황에 편향되어 있습니다.

좋은 모델은 데이터의 한계를 마법처럼 없애 주지 못합니다.

데이터가 현실을 충분히 담지 못하거나 라벨 기준이 흔들리면, 모델은 그 결함까지 규칙으로 학습합니다. 따라서 성능 문제를 모델 구조만의 문제로 해석해서는 안 됩니다.

4. 빙산으로 보는 ML 시스템

Sculley 등은 모델 코드보다 주변의 데이터·운영 작업이 훨씬 크다고 지적했습니다.

데이터 의존성, 수집 시스템, 검증, 모니터링은 모델 코드 밖에 있지만 서비스 신뢰성을 좌우합니다. 이를 임시방편으로 연결하면 시간이 지날수록 수정 비용이 커지는 기술 부채가 됩니다.

Sculley et al. (2015), Hidden Technical Debt in Machine Learning Systems

기술 부채는 어떻게 쌓이는가

초기의 편의 시간이 지난 뒤의 비용
출처와 버전을 기록하지 않음 결과를 재현하거나 원인을 추적하기 어려움
원본과 정제본을 한곳에 저장 무엇이 바뀌었는지 확인하기 어려움
검증 없이 다음 단계로 전달 오류가 배포 직전에 발견되어 전면 재작업
담당자의 수작업에 의존 담당자가 바뀌면 파이프라인이 멈춤

데이터 파이프라인은 처리 속도뿐 아니라 미래의 변경 비용을 줄이는 설계입니다.

5. 데이터 캐스케이드

초기 단계의 작은 데이터 오류가 뒤 단계로 전달되며 커지는 현상입니다.

초기에는 샘플 몇 개의 사소한 문제처럼 보입니다.

나중에는 시스템 전체를 다시 만들어야 할 수 있습니다.

Sambasivan et al. (2021), Data Cascades in High-Stakes AI

6. 데이터 작업이 저평가되는 이유

모델 작업 데이터 작업
결과가 빠르게 보임 효과가 간접적으로 보임
새 기술로 주목받기 쉬움 반복적이고 세밀한 작업이 많음
정확도 숫자로 표현하기 쉬움 기준·문서·협업이 필요함
데모가 화려함 사고를 예방하는 역할이 큼

눈에 덜 띄는 작업이 중요하지 않은 작업은 아닙니다.

데이터 작업은 반복적이고 성과가 예방의 형태로 나타나기 때문에 저평가되기 쉽습니다. 그러나 기준을 문서화하고 오류를 조기에 차단하는 일이 모델의 성능과 안전을 동시에 지탱합니다.

10. 데이터 파이프라인이란?

여러 원천의 데이터를 받아 사용 가능한 형태로 가공하고 목적지까지 전달하는 연결된 처리 과정입니다.

입구

웹·API·DB·파일·IoT

처리

저장·정제·검증·라벨링

출구

분석·서비스·AI 모델

파이프라인은 단순한 작업 목록이 아닙니다. 각 단계의 입력·출력·품질 기준·실패 처리·변경 이력을 연결해 같은 처리를 반복 가능하게 만드는 시스템입니다.

좋은 파이프라인의 네 가지 조건

조건 의미
재현성 같은 입력과 규칙으로 같은 결과를 만들 수 있음
추적성 결과가 어느 원천과 변환에서 왔는지 확인 가능
검증 가능성 단계별 품질 기준을 자동으로 검사 가능
복구 가능성 실패 시 원본이나 이전 단계에서 다시 실행 가능

파이프라인의 가치는 “한 번 성공”이 아니라 데이터와 요구가 바뀌어도 안정적으로 다시 실행되는 데 있습니다.

핵심 질문: 어디에서, 어떤 권한으로, 얼마나 자주, 어떤 형식으로 가져올 것인가?

13. ② 적재

가져온 데이터를 나중에 다시 사용할 수 있도록 저장소에 쌓는 단계입니다.

나쁜 적재

구조가 제각각이고 원본과 가공본이 섞입니다.

좋은 적재

구조·규칙·시점·출처가 명확하고 재처리할 수 있습니다.

14. ③ 정제·변환

문제 정제·변환 예시
비어 있는 값 결측 원인 확인, 대체 또는 제외
같은 대상의 중복 중복 기준을 정하고 제거
날짜 형식 혼재 표준 형식으로 변환
단위 불일치 cm·m 또는 원·달러 통일
잘못된 값 규칙과 원천 대조로 수정

15. ④ 검증

정제한 데이터가 품질 기준을 만족하는지 자동으로 점검합니다.

assert age.between(0, 120).all()
assert customer_id.notna().all()
assert order_id.is_unique

사람이 한 번 눈으로 본 것은 검사이고, 반복 가능한 규칙으로 만든 것은 품질관리 시스템입니다.

19. ETL과 ELT

같은 세 동작을 사용하지만 순서가 다릅니다.

ETL에서 ELT로 이동한 배경

초기의 데이터 시스템은 저장 공간과 계산 자원이 비쌌습니다. 따라서 저장 전에 필요한 형태로 변환하고 불필요한 데이터를 줄이는 ETL이 합리적이었습니다.

클라우드 저장소가 저렴해지고 데이터베이스 안에서 대규모 변환을 수행할 수 있게 되면서, 원본을 먼저 적재한 뒤 필요할 때 변환하는 ELT가 널리 사용됩니다.

ELT의 핵심 이점은 속도 자체보다 원본 보존, 재처리, 다양한 목적의 재사용입니다.

Densmore (2021); Kleppmann (2017)

20. ETL: 넣기 전에 다듬기

Extract → Transform → Load

장점

  • 저장 전 품질과 형식 통제
  • 필요한 데이터만 저장

한계

  • 버린 정보 복구가 어려움
  • 요구 변경 시 앞 단계 재수행

21. ELT: 원본부터 보존하기

Extract → Load → Transform

장점

  • 원본 보존과 재처리
  • 여러 목적에 유연함

주의

  • 원본 영역 관리 필요
  • 접근 권한과 개인정보 보호

22. 냉장고 비유

ETL — 작은 냉장고

채소를 미리 손질해 필요한 것만 넣습니다.

ELT — 큰 창고

원재료를 보관하고 요리할 때 손질합니다.

23. 원본 보존의 원칙

변환 로직이 틀렸다면 어디로 돌아갈까요?

원본을 덮어썼다면 되돌릴 기준점이 없습니다.

원본이 남아 있으면 규칙을 고쳐 몇 번이든 다시 정제할 수 있습니다.

Raw는 보존하고, 가공 결과는 새로 만든다.

24. 이번 과목의 선택: ELT

  • 원천 데이터를 먼저 SQLite에 적재합니다.
  • SQL로 정제·변환합니다.
  • 원본과 결과를 분리합니다.
  • 규칙이 바뀌면 다시 실행합니다.

Raw/Staging은 원천을 최대한 그대로 보존하는 영역이고, Production은 정제·검증을 통과해 실제 분석과 학습에 사용하는 영역입니다. 두 영역을 분리하면 원본 훼손 없이 변환 규칙을 개선할 수 있습니다.

25. 데이터 품질의 정의

“오류가 없는 데이터”면 품질이 좋은가요?

사용하기에 적합한 정도 — Fitness for Use

같은 데이터도 무엇에 쓰는가에 따라 충분할 수도, 부족할 수도 있습니다.

Wang & Strong (1996), Beyond Accuracy

26. 품질은 목적에 따라 달라진다

소수점 첫째 자리까지 기록한 체온 데이터가 있습니다.

감기 선별

발열 여부 판단에는 충분할 수 있습니다.

정밀 의료 연구

미세한 변화 추적에는 부족할 수 있습니다.

27. 데이터 품질의 여섯 얼굴

품질 지표 핵심 질문 나쁜 예시
완전성 있어야 할 값이 있는가? 고객 나이 40% 결측
유효성 형식·범위를 지키는가? 나이 -5, 999
정확성 현실과 일치하는가? 서울을 부산으로 기록
일관성 값끼리 모순이 없는가? 2000년생인데 15세
유일성 불필요한 중복이 없는가? 같은 주문 3번
다양성 집단에 치우치지 않는가? 얼굴 95%가 20대

품질 6차원을 함께 보는 법

여섯 지표는 서로 대체되지 않습니다. 값이 존재해 완전성을 만족하더라도 범위를 벗어나면 유효성이 낮고, 형식이 맞아도 현실과 다르면 정확성이 낮습니다. 품질 평가는 목적에 필요한 차원을 조합해 수행합니다.

28. 완전성: 값이 있는가?

Completeness = 필요한 값이 빠지지 않은 정도

missing_rate = df["age"].isna().mean()
  • 필수 필드가 비어 있지 않은가?
  • 특정 집단에서만 결측이 많지 않은가?
  • 결측 자체가 의미를 가지지는 않는가?

29. 유효성: 규칙을 지키는가?

Validity = 값이 정해진 형식·범위·도메인을 만족하는 정도

항목 유효성 규칙 예시
나이 0 이상 120 이하
이메일 정해진 문자열 형식
성별 코드 {M, F, U} 중 하나
날짜 YYYY-MM-DD 형식

30. 정확성: 현실과 맞는가?

Accuracy = 기록된 값이 실제 세계의 값과 일치하는 정도

서울과 부산은 모두 유효한 문자열입니다. 실제 거주지가 서울인데 부산으로 기록되었다면 부정확합니다.

신뢰할 수 있는 원천과 대조

정답 원천이 없거나 변할 수 있음

31. 일관성: 함께 봐도 맞는가?

Consistency = 여러 값·테이블·시점 사이에 모순이 없는 정도

birth_year = 2000
age        = 15       ← 현재 시점과 모순
  • 주문 합계와 품목 금액의 합
  • 고객 테이블과 주문 테이블의 ID
  • 어제와 오늘의 상태 변화 규칙

32. 유일성: 하나가 한 번만 있는가?

Uniqueness = 동일한 실체가 불필요하게 중복되지 않은 정도

order_id customer amount
1001 김하늘 25,000
1001 김하늘 25,000
1002 이바다 18,000

중복 주문은 매출을 부풀리고 모델 평가도 왜곡할 수 있습니다.

33. 다양성: 현실을 골고루 담았는가?

Diversity = 필요한 집단·상황·조건을 충분히 포괄하는 정도

전체 정확도가 높아도 소수 집단의 성능은 낮을 수 있습니다.

34. 지표는 서로 다르다

age = 999라는 값 하나를 살펴봅시다.

질문 판단
값이 있는가? 완전성은 만족
허용 범위인가? 유효성은 실패
실제 나이와 같은가? 정확성도 실패 가능
생년월일과 맞는가? 일관성도 실패 가능

어떤 품질 차원이 왜 실패했는지 구분해야 해결할 수 있습니다.

35. 품질 기준을 측정 가능하게

모호한 기준

“결측값이 너무 많지 않아야 한다.”

측정 가능한 기준

“필수 열의 결측률은 1% 미만이다.”

지표 정의 → 목표값 설정 → 자동 측정 → 실패 처리 → 기록

36. 데이터 생애주기

37. 1-Cycle 자가점검

  1. 소량의 원천 데이터를 수집합니다.
  2. 정제·라벨링·검증까지 수행합니다.
  3. 목표와 품질 기준을 만족하는지 확인합니다.
  4. 문제가 크면 방법과 기준을 빠르게 수정합니다.

초기에 작게 실패하면 전체 구축 이후 크게 실패하는 비용을 줄일 수 있습니다.

39. 데이터의 세 가지 형태

구분 구조 대표 예시
정형 행·열과 스키마가 명확 관계형 DB, CSV, Excel
반정형 키 구조는 있으나 유연 JSON, XML, 로그
비정형 고정된 격자 구조가 없음 이미지, 음성, 영상, 자연어

구조화 정도에 따라 수집·저장·검증·라벨링 방법이 달라집니다.

데이터 형태를 그림으로 비교

AI 학습에서는 비정형 데이터가 중요하지만, 파일명·출처·촬영일·해상도·라벨 같은 메타데이터는 정형 테이블로 관리합니다. 따라서 관계형 데이터베이스는 비정형 데이터 프로젝트에서도 중심 관리 대장이 됩니다.

40. 비정형 데이터도 관리표가 필요하다

file_id filename width height label source
1 img_001.jpg 1920 1080 cat camera_A

관계형 데이터베이스는 비정형 파일의 관리 대장(catalog) 역할을 합니다.

41. 왜 SQLite인가?

설치 장벽이 낮음

Python에 기본 포함

파일 하나

복사·백업·공유가 쉬움

진짜 SQL

큰 DB로 지식 확장

SQLite는 서버 프로세스 없이 애플리케이션 안에서 동작하는 임베디드 데이터베이스입니다. 파일 하나로 상태를 확인할 수 있으면서도 SELECT, JOIN, GROUP BY, 트랜잭션 같은 관계형 데이터베이스의 핵심 개념을 그대로 연습할 수 있습니다.

42. SQLite의 구조

용어 의미
Database 여러 테이블을 담는 저장소
Table 같은 구조의 레코드 집합
Row 하나의 대상·사건 레코드
Column 레코드가 가진 속성

43. 기본 키와 외래 키

  • 기본 키(PK): 각 행을 고유하게 구분합니다.
  • 외래 키(FK): 다른 테이블의 행을 참조합니다.

44. Python과 SQLite의 대화 순서

connect → cursor → execute → commit/rollback → close

import sqlite3
conn = sqlite3.connect("students.db")
cur = conn.cursor()
cur.execute("SELECT * FROM students")
rows = cur.fetchall()
conn.close()

45. 트랜잭션: 전부 아니면 전무

출금만 되고 입금이 실패한 중간 상태가 저장되어서는 안 됩니다.

46. 안전한 SQL: 플레이스홀더

위험한 방식

sql = "SELECT * FROM users WHERE name='" + name + "'"
cur.execute(sql)

안전한 방식

cur.execute(
  "SELECT * FROM users WHERE name=?",
  (name,)
)

48. 품질은 윤리의 문제다

  • 의료 데이터 오류는 진단 기회를 빼앗을 수 있습니다.
  • 편향된 채용 데이터는 특정 지원자를 부당하게 배제할 수 있습니다.
  • 잘못된 신용 데이터는 금융 접근성을 제한할 수 있습니다.
  • 부정확한 공공 데이터는 잘못된 정책을 만들 수 있습니다.

데이터를 구축하는 판단은 모델의 행동과 실제 사람의 삶으로 이어집니다.

데이터 구축자는 어떤 사례를 포함하고 제외할지, 무엇을 정답으로 볼지, 어떤 오류를 허용할지를 결정합니다. 이 판단은 모델의 행동 범위와 실패 대상을 결정하므로 품질관리는 기술적 검사이면서 윤리적 책임입니다.

54. 마무리 확인 문제

  1. 데이터 캐스케이드란 무엇인가요?
  2. ETL과 ELT의 가장 큰 차이는 무엇인가요?
  3. age = 999는 어떤 품질 지표를 위반하나요?
  4. 이미지 프로젝트에서도 SQLite가 필요한 이유는 무엇인가요?
  5. commit과 rollback은 각각 어떤 역할을 하나요?

2분간 짝과 답을 비교한 뒤 전체 답을 확인한다.

확인 문제 1 정답: 데이터 캐스케이드

정답: 초기 데이터 단계의 작은 오류가 파이프라인을 따라 전달되고 증폭되어 모델과 서비스 전체의 문제로 커지는 현상입니다.

해설: 수집이나 라벨링에서 발생한 오류는 학습과 평가를 거쳐 잘못된 배포 판단으로 이어질 수 있습니다. 이를 줄이려면 원본을 보존하고 단계마다 데이터를 검증해야 합니다.

확인 문제 2 정답: ETL과 ELT

정답: 가장 큰 차이는 변환(Transform)과 적재(Load)의 순서입니다. ETL은 추출 → 변환 → 적재, ELT는 추출 → 적재 → 변환 순서입니다.

해설: ETL은 저장 전에 데이터를 다듬고, ELT는 원본을 먼저 저장한 뒤 저장소에서 변환합니다. ELT는 원본을 보존하므로 변환 기준이 바뀌었을 때 다시 처리하기 쉽습니다.

확인 문제 3 정답: age = 999

정답: 유효성(Validity)을 위반합니다.

해설: 나이는 일반적으로 정해진 허용 범위 안에 있어야 합니다. 999는 형식상 숫자이고 값도 존재하지만 허용 범위를 벗어나므로 유효하지 않습니다. 실제 나이와도 다르므로 정확성 문제로 이어질 수도 있습니다.

확인 문제 4 정답: 이미지와 SQLite

정답: 이미지의 메타데이터와 라벨 정보를 체계적으로 관리하기 위해 SQLite가 필요합니다.

해설: 이미지 파일은 비정형 데이터지만 파일명, 저장 경로, 크기, 출처, 라벨, 검수 상태 등은 정형 데이터입니다. SQLite는 이러한 정보를 이미지와 연결해 조회하고 검증하는 관리 대장 역할을 합니다.

확인 문제 5 정답: commit과 rollback

정답: commit()은 변경 내용을 확정하고, rollback()은 아직 확정하지 않은 변경 내용을 취소합니다.

해설: 여러 데이터 변경이 모두 성공하면 commit()을 호출합니다. 작업 중 하나라도 실패하면 rollback()을 호출해 일부 변경만 저장되는 상태를 방지합니다.
